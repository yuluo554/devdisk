# 10-18-dev-disk-audit · 开发者磁盘占用审计与安全清理（题目文档）

> - **性质**：不参赛项目题（无赛事锚点；含金量锚点 = 需求侧真实痛点 + 确定性可评测 + 功能增量缝隙）
> - **目标产出**：仓库 `10-18-dev-disk-audit`（DevDiskAudit / 开发者磁盘审计器），发布 GitHub **公开仓库**，署名 yuluo554
> - **版本史**：v1 2026-10-17（初稿定稿，查证基准日 2026-10-17）
> - **交付形态**：**纯本地 Python CLI + 本地单文件 HTML 报告**。单一形态，不设备选：CLI 负责扫描、分级、只读审计、隔离与撤销，HTML 报告负责阅读与复核。**无服务器、无 GPU、无网络调用**。
> - **定位宣言**："开发者磁盘被 node_modules/.venv/构建产物/Docker 镜像缓存/大 .git 对象吃掉，但没人敢删——本工具按'可重建性 + 最后修改时间 + 依赖关系'给出**分级可删清单**，默认只出报告、清理必须显式确认、删除走隔离区可回滚。**安全分级与中文界面是差异化**：已有工具覆盖了多数目录类型，但没人把 Docker 与 .git 纳入统一的安全分级，也没人把'误删的代价'做成可回滚。"
> - **诚实定位**：本题是**功能增量而非新题**。kondo（2451★）已覆盖 20+ 项目类型并内置 `--dry-run` 与 `--older`；npkill（9477★）已垄断 node_modules 清理心智。本题不宣称品类首创，只争取"统一多类型 + Docker 镜像缓存 + .git 对象 + 安全分级 + 中文界面 + 可回滚隔离区"这一窄缝；若开发中砍掉 Docker/.git 审计与隔离区回滚，则退化为 kondo 的复制品，应视为失败。

## 一、介绍

**痛点**：本地开发机被可重建产物长期占用——一个中型前端项目的 `node_modules` 动辄数百 MiB 到数 GiB，Python 项目的 `.venv`/`__pycache__`/`.mypy_cache`/`.tox` 分散在多个仓库，构建目录 `dist`/`build`/`.next`/`target`/`out` 随项目数量线性增长，Docker 的镜像层与构建缓存常以十 GiB 计，老仓库的 `.git/objects` 在历史里越滚越大。用户明知"大部分可以重建"，却因为三件事不敢动手：**不知道哪些真能删、不知道删了以后怎么恢复、不知道删除会不会破坏共享依赖或版本历史**。现有工具解决的是"找出来 + 删掉"，没有解决"分级 + 解释 + 回滚"。

**需求侧证据（✅ 已核对，基准日 2026-10-17）**：

- **npkill 9477★**（TypeScript，2026-10-13 仍活跃），npm **58,924 次/月**（统计窗口 2026-09-13~10-12，数据源 `api.npmjs.org`）。单功能工具接近每月六万次下载，说明 node_modules 清理痛点真实且高频。
- **kondo 2451★**（Rust，快照日期 2026-04-24），README 自称覆盖 **20+ 项目类型**；源码 `kondo-lib/src/lib.rs` 常量可查：Node、React Native、Python（`__pycache__`/`.mypy_cache`/`.tox` 等）、Gradle、Maven、SBT、CMake、Unreal、Unity、.NET、Terraform、CocoaPods 等，**已内置 `--dry-run` 与 `--older`**。
- **B 站中文需求侧独立存在**（✅ 条目原文）：「如何快速检索 node_modules」「快速删除 Node_modules 目录，减少磁盘空间占用」「全平台可用-批量删除 node_modules」「npkill 清理老旧的 node_modules 文件夹」。这些内容证明中文用户有独立于英文工具的检索与教程需求，但本身不是量化市场证据。

**竞品覆盖事实与缝隙范围（⚠ 缝隙很窄，如实记录）**：

- kondo 已覆盖 80% 左右的常见目录类型，且自带 dry-run 与按时间过滤；npkill 在 node_modules 单点上拥有压倒性的用户心智。这两块**不是本题的增量**。
- 本题能争取的增量只有四处：**① 把 Docker 镜像/容器/卷/构建缓存纳入同一份只读审计；② 把 `.git/objects` 与 pack 体积纳入同一份清单（只建议 `git gc`，永不删除）；③ 每个条目给出可解释的三级安全分级与证据；④ 所有删除走隔离区、可一键撤销，并提供中文 HTML 报告。**
- GitHub 检索快照（⬜ 软论据，检索式与基准日可回溯，未做入库截图）：`disk cleaner CLI` → 135；`developer cache cleaner` → 114；`node_modules cleaner` → 145（单类型高度拥挤）；`docker prune tui` → **3**；`docker prune gui` → **0**；`git gc large repo cleanup tool` → **0**；`developer disk space cleanup windows gui` → **0**；中文 `磁盘清理` → 仅 DawnyFY/FluffyDiskCleaner 且 **0★**（Windows 系统清理，非开发产物）。这些数字只作辅助判断，不能与"原文直连核对"并列作硬锚点。
- **判定：缝隙很窄。** 本题的价值不在"发现没人做过磁盘清理"，而在"把 Docker、.git、多类型缓存统一进一套可解释、可回滚的安全分级"。

**误删风险（最高优先级风险，必须如实告知用户）**：

- `<venv>/bin` 可能是软链接，跟随符号链接统计或删除会误伤系统 Python；扫描必须**不跟随 symlink**，跨出扫描根的目标一律跳过并记录。
- monorepo 中多个 workspace 可能共享同一份 `node_modules`（软链或 hoisting）；按目录独立删除可能破坏未预期的工作区。
- **手工删除 `.git/objects` 会直接毁掉版本历史**，且多数情况下不可恢复。本题对 `.git` **只读统计、只输出建议、永不自动处理**。
- 构建产物目录里可能混有手工文件（`dist` 里放了未提交的配置、`.env` 放在项目根或缓存目录旁），因此"可重建"必须由证据支撑，而不是按目录名一刀切。
- **产品纪律**：所有删除动作先移动到隔离区（移动而非 `rm -rf`），写 manifest，支持一键撤销；任何"建议"都不自动执行。

**技术栈（✅ 成熟依赖）**：Python 标准库即可完成目录遍历、体积统计、JSON/HTML 生成；Docker 审计调用 `docker system df`（只读），缺少 Docker CLI 时显式降级；`.git` 审计直接读 `objects/pack` 体积与文件计数，不调用任何写操作。无需网络、无需 GPU、无需数据库服务。

## 二、任务要求

首期 **5 个模块**，扩展项另列。每模块写清 **输入 / 输出 / 确定性纪律 / 验收**。所有模块共享 `data/README.md` §四的数值口径，不得在代码或文案中另立第二套口径。

### 模块①：扫描与分类

- **输入**：一个或多个扫描根目录 + 类型规则表 + 忽略规则 + 候选体积阈值。
- **输出**：候选清单（JSON/CSV），每条含：绝对路径、类型标签（node_modules / dist / build / .venv / venv / __pycache__ / .mypy_cache / .pytest_cache / .tox / .next / .cache / target / out 等）、体积（字节）、最后修改时间、所属项目根、是否符号链接、跳过原因。
- **引擎**：`os.scandir` 迭代遍历；**不跟随符号链接**（`entry.is_symlink()` 直接记录并跳过）；同一物理对象用 `(st_dev, st_ino)` 去重，避免硬链接重复计数；Windows 长路径使用 `\\?\` 前缀；权限错误、占用错误逐条记录为 `skipped:<reason>`，不静默丢弃。
- **确定性纪律**：类型规则表单点定义；体积统一按字节累计，展示层再换算；排序规则固定（体积降序，同体积按路径字典序）；同一目录树两次扫描输出逐字节一致（时间字段取自文件系统 mtime，不取扫描时刻）。
- **验收**：1000 个候选目录的合成树扫描不崩溃；构造指向扫描根之外的符号链接与符号链接环，断言不越界、不重复计数、不进入死循环；两次扫描输出一致。

### 模块②：安全分级

- **输入**：模块①的候选清单 + 目录内文件名/元数据证据。
- **输出**：每条候选的三级分级（**安全可删 / 谨慎 / 禁止**）+ 可解释理由字符串 + 证据字段。
- **分级规则（单点定义，优先级从高到低）**：
  - **禁止**：`.git` 目录、扫描根本身、源码目录、用户显式标记为保留的路径、检测到符号链接指向扫描根之外的目录。
  - **谨慎**：目录内存在可能承载本地状态的文件（如 `.env`、`*.local`、未被忽略的手工文件）、目录名命中构建产物但存在构建时间之后的修改、monorepo 共享依赖迹象、`.venv` 中存在非包管理器生成的可执行配置。
  - **安全可删**：纯缓存或纯可重建产物，且有证据表明可重建（如存在锁文件/包清单、目录结构与包管理器缓存一致、无构建后修改）。
- **可解释性要求**：每个条目必须输出理由字符串与证据（如"存在 `.gitignore` 未覆盖的手工文件：`dist/config.local.json`"、"目录内仅有包管理器缓存结构，检测到 `package-lock.json`"）。理由只能引用**路径、体积、mtime 与白名单元数据文件**，不得读取源码或文档正文。
- **确定性纪律**：分级规则命中顺序固定；同一输入两次分级结果一致；证据不足时降级为"谨慎"，不得默认为"安全可删"。
- **验收**：每条候选均有非空理由字符串与至少一条证据；合成真值树中每个样本的分级与植入真值一致；证据不足样本全部落到"谨慎"。

### 模块③：Docker 与 .git 只读审计

- **输入**：可选的 Docker CLI 环境；扫描根下的 Git 仓库列表。
- **输出**：Docker 段（镜像/容器/本地卷/构建缓存的体积与可回收量）+ Git 段（每个仓库的 `objects` 总体积、pack 文件数、loose object 数）+ 建议文本。
- **引擎**：调用 `docker system df`（只读）并解析输出；Docker 缺失或命令失败时输出 `skipped:docker_unavailable` 与原因，**退出码进入降级语义，不得伪装成"没有可清理内容"**。`.git` 段直接遍历 `objects/pack` 与 loose object 目录统计体积与数量；当 loose object 数或 objects 体积超过配置阈值时，输出"建议执行 `git gc`"的建议行。
- **产品纪律（硬约束）**：
  - **`.git` 永不自动处理**：本模块只读，不删除、不移动、不执行 `git gc`，不修改任何仓库文件。
  - **Docker 清理命令只生成、不执行**：输出 `docker image prune` / `docker builder prune` 等建议命令与预估可回收量，是否执行由用户自行决定；本工具不调用任何 prune 子命令。
- **确定性纪律**：Docker 输出解析使用固定字段映射；解析失败显式标记而不是填空值；Git 体积统计口径与模块①一致（字节，不含符号链接）；审计前后对 `.git` 目录做元数据快照，断言未发生变化。
- **验收**：用固定 Docker 文本 fixture 断言四类体积解析正确；对合成 Git 仓库断言 `objects` 体积、pack 数、loose 数正确；审计前后 `.git` 目录文件清单与 mtime 不变；输出中每条建议均带 `applied: false`。

### 模块④：交互式清理与隔离区

- **输入**：用户显式选中的候选（按路径或按批次）+ 确认令牌。
- **输出**：`.trash/<batch-id>/` 下的移动后内容 + `manifest.json`（原路径、隔离路径、体积、分级、理由、mtime、逐文件 sha256/tree digest、状态）+ 可读的批次摘要。
- **引擎**：默认 dry-run，只打印将移动什么；用户显式确认（二次确认字符串或 `--yes` 加交互确认）后，用 `shutil.move` 移动到隔离区，保持相对路径结构；manifest 状态机先写 `pending` 再移动再写 `moved`；撤销时按 manifest 逆序移回，目标路径已存在则拒绝覆盖并报冲突。
- **产品纪律（硬约束）**：
  - **永不直接 `rm -rf`**；隔离区必须与源目录同一文件系统，跨设备时直接拒绝并提示用户改隔离区位置，不得用"复制后删除"绕过。
  - **不做"一键清理全部"**：必须逐条或逐批显式选择；默认只出报告。
  - 撤销前校验 tree digest；撤销后再次校验，保证路径与内容逐字节一致。
- **确定性纪律**：`batch-id` 与隔离区命名单点定义（见 `data/README.md` §四）；manifest 写入顺序固定；中断后按状态机续做或回退，不产生"已移动但无记录"的孤儿。
- **验收**：撤销后原路径逐字节一致（tree digest 相同）；移动中断后可从 manifest 恢复；隔离区、manifest、索引文件均不入 git；任何路径下都不出现 `rm -rf` 调用。

### 模块⑤：本地 HTML 报告与真值基准

- **输入**：模块①–④的产物。
- **输出**：**单文件 HTML**（内联 CSS/JS，零外链、零 CDN、零网络请求），包含：体积排行、按项目/类型聚合、可删合计、三级分级分布、每条分级理由与证据、Docker/.git 只读审计段、清理建议（含"命令只生成不执行"标注）、隔离批次列表与撤销入口说明。
- **引擎**：标准库字符串模板生成；所有数据在生成时嵌入，页面打开后不再请求任何资源；HTML 转义防止路径中的特殊字符破坏页面。
- **确定性纪律**：同一输入两次生成的报告内容一致（不含生成时刻等易变字段，或将其固定为输入的一部分）；合计口径与 `data/README.md` §四一致；报告只陈述测量与建议，不承诺"删了必然安全"。
- **验收（功能验收）**：断网环境双击打开报告可完整阅读；页面无任何外部 URL；报告中的总体积、各级合计、排行顺序与合成真值逐项一致；Docker 缺失时报告显式展示降级说明。

**扩展项（首期不做）**：Windows 长路径与文件占用重试的增强策略、WSL 发行版缓存扫描、定时审计与历史对比、更多语言生态（Ruby/Go/Java 等）的类型规则、macOS `~/Library/Caches` 适配、Linux 系统级缓存（需 root）。

- **受众**：本地同时维护多个项目、磁盘长期紧张的开发者；使用 Docker 与大型 Git 仓库的后端/全栈/移动端开发者；需要向团队解释"为什么这些目录能删"的技术负责人。
- **时代性**：前端依赖体积与 Docker 层缓存持续膨胀，开发机普遍 512 GiB~1 TiB 且长期不重装；大模型可以解释单个目录，却不会持续维护本机清单、不能替用户承担误删后果，也不会提供可回滚的执行层。
- **开源缝隙（功能增量缝隙）**：npkill 与 kondo 已经把"找出来"和"dry-run"做得很成熟；剩下的增量是"统一多类型 + Docker 镜像缓存 + .git 对象 + 可解释安全分级 + 中文界面 + 可回滚隔离区"。本题只做这一层，不宣称品类新。

## 六、边界与非目标

- **不自动删除**：默认只出报告；任何删除必须显式确认并进入隔离区；**永不直接 `rm -rf`**。
- **`.git` 永不自动处理**：只读统计 `objects` 体积与 pack/loose 数量，最多建议 `git gc`；不删除对象、不执行 gc、不修改仓库状态。
- **不做系统级清理**：不碰系统缓存、回收站、软件卸载、注册表、`/tmp` 之外的系统目录；这些是专业清理工具的领域，且常需管理员权限。
- **不做云盘/同步盘文件**：不扫描 OneDrive/iCloud/坚果云等同步目录，避免删除动作触发跨端同步与不可逆传播。
- **不做重复文件查找**：已有成熟工具覆盖；本题只按"可重建性"分级，不按内容哈希找重复。
- **不做"一键清理全部"**：这是误操作的最大入口；必须逐条或逐批选择。
- **首期范围限定**：仅上述 5 个模块；WSL、macOS `~/Library/Caches`、定时审计、更多语言生态留扩展项。
- **隐私红线**：只扫描路径、体积、mtime 与白名单元数据文件（`.gitignore`、包清单）用于分级证据；**不读取源码/文档正文、不上传任何数据、无遥测、无网络请求**。HTML 报告只在本机打开。
- **品牌隔离**：本题定位为独占的"开发者磁盘占用审计与安全清理"工具；命名、文案、代码命名空间均围绕"磁盘 / 体积 / 分级 / 隔离"词系；文档**不提及本系列任何其他项目**。
- **结论纪律**：分级是**基于可观察证据的建议**，不是"删除后必然安全"的保证；用户需自行确认重建成本；报告只陈述测量值与理由，不替用户做删除决策。
- **平台差异告知**：Windows 存在文件占用与 260 字符长路径、大小写不敏感、Docker Desktop 与 WSL 两套缓存；macOS 需处理 `~/Library/Caches`；Linux 清理系统级缓存需 root。首期只保证扫描与隔离在主力平台可用，其余差异在报告与文档中显式说明。
